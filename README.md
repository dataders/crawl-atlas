# Crawl Atlas

A spoiler-safe reading companion for LitRPG books. Move one slider to the point you have reached and see the party's complete known history, levels, stats, skills, and active inventory—never facts first revealed later.

The current dataset maps all eight *Dungeon Crawler Carl* books. This repository does **not** redistribute the books: EPUB files, extracted prose, and machine-generated review candidates remain local and are ignored by Git.

## What works

- EPUB-to-JSON corpus extraction using only Python's standard library
- one continuous, series-wide progress control with book, chapter, and paragraph anchors
- candidate detection for levels, stats, skills, items, rewards, and party changes
- source-anchored character and inventory audits
- cumulative level and base-stat charts with explicit milestone labels
- filterable dossiers for the core party, support characters, and major recurring allies
- inventory ledger and event history
- dbt Charts dashboard with character, metric, and through-book selectors
- strict location filtering so every view respects the reader's spoiler boundary

## Local setup

1. Put your legally obtained EPUBs in this directory using the filenames listed in `scripts/extract_series.py`.
2. Extract the private eight-book analysis corpus:

   ```bash
   uv run python3 scripts/extract_series.py
   ```

3. Serve the static site:

   ```bash
   uv run python3 -m http.server 4173 --directory site/dist
   ```

4. Open `http://localhost:4173`.

The checked-in public data contains short factual summaries, not book text. To rebuild it after improving the private audits, run:

```bash
uv run python3 scripts/build_public_timeline.py
uv run python3 scripts/validate_data.py site/dist/data/series.json --corpus data/private/series-corpus.json
uv run python scripts/build_charts_data.py
uv run python scripts/build_database.py
dct validate charts/crawl-atlas.yml --strict
```

## Progression ledger and SQL database

One reading slider controls charts, the progression ledger, character dossiers,
inventory, rewards, and history on a single page. Header links jump between sections.
The board’s progression ledger lists observations newest first, twelve per page.
Use **Filter characters in the detail sections** to narrow dossiers, inventory,
rewards, and history. The board’s level and stat plots include all known characters. Inside the board,
the **Character** dropdown changes only the dossier. The **Owner** dropdown
and item search change only inventory. These controls select dbt-rendered
table rows in the browser at the exact slider position. Native dbt query
variables require a live query host such as dbt Charts Cloud or `dct serve`.
Dossiers label levels with their last-observed book and chapter. New sessions start
at the beginning. Reading position is retained in the URL.

`site/dist/data/crawl-atlas.sqlite` contains all curated public events, with indexed
`events` and `progression` tables, a `books` table, and an `increases` view. The UI
uses `progression.json`, generated by the same build. Rebuild both after changing
`series.json`:

```bash
uv run python scripts/build_database.py
sqlite3 site/dist/data/crawl-atlas.sqlite
```

For example, find Carl's level increases through the end of Book 1:

```sql
SELECT book, chapter, metric, previous, value, delta, source
FROM increases
WHERE character = 'Carl' AND kind = 'level' AND book <= 1
ORDER BY progress;
```

Trace skill observations at a precise spoiler boundary (progress ranges 0–1):

```sql
SELECT character, metric, value, delta, confidence, source
FROM progression
WHERE kind = 'skill' AND metric LIKE '%Magic%'
  AND progress <= 0.04
ORDER BY progress;
```

The raw database contains all books; SQL callers must apply their own reading
boundary. The reader applies it before building each chart and paginated table.
The EPUB prose stays in the private local corpus. SQLite supports direct SQL
queries over all event facts, including inventory and story records in `events`.

Each stat in a multi-stat event has its own row. Deltas compare earlier numeric
observations with the same character, metric, scope, and confidence. First values
remain unknown rather than starting at zero. Explicit modifier-only events retain
the stated delta without inventing an absolute value; subsequent comparisons reset.
Reported skill observations can include equipment effects and are not claimed as
base skill growth. Book 8 now has a 98-chapter scan for explicit tracked-cast progression, with the
reviewed factual records in `data/public/book-8-audit.json`. Books 2–7 still have
selective coverage. One-off monster and NPC status screens are not part of this
character roster. Book 8 skill scopes distinguish equipment, granted spells,
class benefits, permanent boons, base levels, and effective casting levels.
Repeated character-level confirmations remain separate observations with zero
change, preserving the latest confirmation date. Percentage equipment bonuses
stay in item summaries; they never become absolute stat totals.

## dbt Charts dashboard

The page opens with the static HTML board exported by dbt Charts. Its latest-level
table shows the most recent observation for each character at the slider position.
Run `uv run python scripts/render_reader_charts.py` after rebuilding the public SQLite data.
The reading slider selects the latest visible checkpoint across the cast. Level fills the first row, followed by a two-by-two stat grid, or one column on narrow screens.
All observed characters are included.

The four stat panels show explicitly recorded **base** values. Equipment and temporary
observations appear in the progression ledger. Points mark observations;
lines connect those observations across gaps in the text.

Pages serves the checkpoint HTML in `site/dist/charts/`. Changes to the local
interactive board do not change that HTML. Regenerate the reader after editing its
inputs or generator, then commit the exports and `charts/reader-exports.json` together.
The Pages job checks their hashes before upload. Legacy SVG snapshots in
`site/dist/reader-charts/` are excluded from the production artifact.
The interactive local board is also available below.

The dashboard reads the same generated public SQLite snapshot as the website; it
needs no warehouse credentials. Install dbt Charts from the latest Dataface release
tag and start the interactive board:

```bash
uv tool install --force \
  "dbt-charts @ git+file://$HOME/Developer/dataface@dbt-charts-v0.11.0#subdirectory=dbt-charts"
dct serve
```

To test improvements from Dataface `main` before their next release:

```bash
git -C ~/Developer/dataface pull --ff-only
uv tool install --force ~/Developer/dataface/dbt-charts
```

`dct serve` provides the working character multiselect, metric selector, book
slider, tabs, and URL-persisted filter state. A static HTML export is useful as
a snapshot, but its variable controls are not interactive:

```bash
dct render charts/crawl-atlas.yml --format html --output renders/crawl-atlas.html
```

Community references may seed audit candidates, but a value is published only after it is independently confirmed against the local EPUB and classified as a base value, equipment-modified total, temporary effect, or reported total.

## Data model

Each event has a `book`, local `chapter`, fractional `position`, and computed series-wide `progress`. The app replays every event at or before the reader's chosen location to reconstruct the current state. Event types include character levels, stats, skills, inventory changes, party changes, and brief story milestones. Entries carry:

- `confidence`: `verified`, `inferred`, or `needs-review`
- `action`: how the event changes the current state
- `subject`: the affected character or party
- `source`: a private corpus anchor used for validation; source prose is not published

See [`schema/book-timeline.schema.json`](schema/book-timeline.schema.json).

### Private sentence evidence (DuckDB + Parquet)

Build locally with `uv run --with duckdb python scripts/build_evidence_database.py`.
This creates `data/private/evidence/crawl-atlas.duckdb` and four Zstandard Parquet
exports. These contain copyrighted source text, remain gitignored, and are never
copied into `site/dist` or a deployment archive. The hosted app still uses public
JSON facts and the downloadable SQLite snapshot; it does not query this private
DuckDB database.

- `sentences`: every extracted sentence, original paragraph, character offsets,
  book/chapter/paragraph location, sentence ordinal within chapter and paragraph,
  and a stable paragraph-based sentence ID.
- `observations`: one character/attribute observation per row, with attribute name,
  numeric value and delta when stated, scope, action, confidence, summary, and
  the reveal location. Includes items and narrative observations as well as levels.
- `observation_evidence`: many-to-many links from observations to source sentences.
  Curated sentence links are marked `sentence`; legacy paragraph citations are
  marked `paragraph`, and expose all sentences in that paragraph as context.
- `character-evidence.parquet` / `character_evidence` view: convenient joined form
  with `character`, `book`, `chapter`, `sentence`, `attribute`, `attribute_name`,
  `value`, `source_sentence`, and evidence precision.

Sentence splitting uses versioned punctuation heuristics. It preserves exact text
and offsets but is not an editorial sentence count. Original paragraph anchors
remain authoritative. A `manifest.json` records input hashes and row counts.
Observations are curated, **not an exhaustive extraction of every fact**; raw
`sentences` and `imani_mentions` support searching for omissions independently.

```sh
uv run --with duckdb python scripts/query_evidence.py "
  SELECT character, book, chapter, sentence, attribute, value,
         source_sentence, evidence_precision
  FROM character_evidence
  WHERE character = 'Imani C.' AND attribute = 'level'
  ORDER BY book, chapter, paragraph, sentence
"
```

Direct Parquet equivalent in DuckDB:

```sql
SELECT character, book, chapter, sentence, attribute_name, source_sentence
FROM read_parquet('data/private/evidence/character-evidence.parquet')
WHERE character = 'Imani C.' AND attribute = 'skill'
ORDER BY book, chapter, paragraph, sentence;

-- Search source text independently of the curated observations.
SELECT book, chapter, sentence, source_sentence
FROM read_parquet('data/private/evidence/sentences.parquet')
WHERE source_sentence ILIKE '%Imani%';
```

For now, DuckDB + Parquet is sufficient for this local, single-writer collection.
DuckLake would become useful for shared writers, catalog-managed snapshots/time
travel, or a growing object-storage dataset; it is not required to query Parquet.

### Imani audit, Books 1–8

`data/public/imani-audit.json` adds source-anchored progression and equipment
observations. The private `data/private/imani-audit-review.md` records the search
method and excluded attributions. This was a targeted name/alias/context audit,
including an independent review of numeric candidates, not a claim of a linear
reread of every paragraph.

Imani's first level-10 observation is Book 1, chapter 22; she reaches 11 in
chapter 27 and is explicitly 24 in Book 3, chapter 8. Book 5, chapter 36 names her
in a group that has gained several levels, without giving her total. This is an
`increase` event with a null value and delta, included by the SQL `increases` view
and the website's increases filter. It invalidates carrying forward 24 as a
current total. No newer exact numeric total was found in the targeted audit.
Charts end at the last exact observation; dashed guides do not estimate when
unreported gains happened. Temporary Tripper grants do not inherit Carl's level7.

### Boxes, rewards, and acquisition chains

The `Boxes & rewards` tab follows the cast selection and reading boundary. It
filters by stage, tier, type, and text, and shows the source chain for each reward.
Initial coverage reuses Book 1 opening batches and adds selected explicit box
lineages in Books 1, 5, and 8. This is not a completed eight-book box audit.

A reward uses linked events, not one overloaded source-detail field:

```
boss victory / achievement / sponsorship
  → box awarded → box opened → item / boon received → effect applied
```

`acquisitions` and `acquisition_links` are in both public SQLite and private DuckDB.
The joined `character-evidence.parquet` also includes acquisition columns.
Private exports include `acquisitions.parquet`, `acquisition_links.parquet`, and
`acquisition-evidence.parquet` (with the original evidence sentences).

Important columns:

- `source_type`: immediate mechanism, such as `reward_box`, `opening_batch`, or
  `sponsorship`. `source` remains the original text anchor, a different concept.
- `box_id`: identifies the particular box across award/opening/detail records.
- `box_tier`: Bronze, Silver, Gold, Platinum, Legendary, Celestial.
- `box_kind`: Pet, Boss, Benefactor, Slap-Chop, etc. Benefactor is not a tier.
- `stage`: trigger, awarded, opened, received, identified, or applied.
- `outcome_type`: supports physical items, boons, and skill modifiers.
- `reason_type` and `reason_detail`: describe the root reward trigger.
- `parent_event_id`: in `acquisition_links`, preserves causal steps and recipients.
- `book`, `chapter`, `progress`, `source`: when the evidence is revealed.
  `occurrence_detail` records retrospective timing without inventing a date.
- `attribution`: `explicit` or `batch`. A batch opening does not establish which
  individual box supplied an item. Unknown box tiers and causes stay null.

For example, Imani's Benefactor Box is received/opened in Book 5, Chapter 57;
its Silver tier is not revealed until Chapter 62. The UI only resolves that tier
once the slider passes the later evidence. An intended gift is not a completed
transfer. Each linked event retains its own source and confidence.

```sql
-- Boxes awarded, rather than counting openings again as new boxes.
SELECT character, name, box_tier, box_kind, quantity, book, chapter
FROM acquisitions WHERE stage = 'awarded';

-- Immediate item source. Continue joining parent IDs to reach its root cause.
SELECT item.character, item.name AS item, box.name AS immediate_source,
       box.box_tier, box.box_kind
FROM acquisitions item
JOIN acquisition_links link ON link.child_event_id = item.event_id
JOIN acquisitions box ON box.event_id = link.parent_event_id
WHERE item.stage = 'received';
```
